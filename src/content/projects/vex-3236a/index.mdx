I've been on VEX teams since **2021**. In middle school I ended up leading the team, and we made it to the **VEX World Championship twice**. In high school I captain **team 3236A**, a team of 8.

This page is about the Push Back season and how the team runs. For the FRC team I'm helping restart, see [Tri-County FRC](/projects/tri-county-frc/).

## The problem

Every VEX season has a **new game**. The field, the scoring objects and the rules all change, so last year's robot is mostly scrap. Each season you have to figure out what wins, build a robot that does it, write code for it, and drive it well under pressure.

You also have to do that with a team. Eight students, all my age. The robot is only as good as how the team splits the work.

## The solution

As captain for **Push Back**, I led three things:

- **The design process:** reading the game, picking a robot concept, and getting a driving base built early.
- **The code:** C++ on **EZ-Template**, so time goes into routes and mechanisms instead of drive math.
- **Competition strategy and execution:** which autonomous routine to run, what to tell our alliance partner, and what to change between matches.

## How it works

### Design process

Before anyone builds, we work out how matches are scored and what a winning robot has to do. Then we sketch options, pick one, and get a drivetrain moving as fast as possible so the drivers can start practicing.

### Code

I write our code in **C++** on **EZ-Template**, an open-source library for **VEX V5** built on PROS. It handles the drivetrain **PID** control and the on-screen **autonomous selector**.

Why use it: drive control is the same problem every season. A tested library for it means my time goes into autonomous routes and mechanism code, which is where the game actually changes.

At events I handle strategy: picking the autonomous routine for each match based on our alliance and opponents, talking through the plan with our partner before the match, and deciding what to fix between matches when something breaks.
